## 1. Security audit scope

The review covered the whole application source and its route, database, storage, build, and dependency configuration, with adversarial HTTP probes against a local Next.js server backed by a throwaway SQLite/libSQL database.

- **Authentication and sessions:** Argon2id password hashing; uniform credential failures; session-token generation, digest-only persistence, expiry, revocation and account deactivation; cookie attributes; login throttling and lockout; forced password change; operator recovery; and double-submit CSRF validation.
- **Authorization:** authenticated page layouts and direct page access; API guards and role checks; owner-only SEO/site settings; editor permissions; assessment roles; and record/attachment identifier pairing.
- **Assessment submission:** multipart-only requests, request and answer size checks, server-side schema and file validation, consent-version checks, honeypot/rate limits, idempotency and duplicate detection, response privacy, and transaction/rollback behavior.
- **CV and CMS media:** MIME/signature checks, size limits, private/public store separation, media metadata and mutation routes, path traversal, public proxy allowlists, download headers, and archive handling.
- **CMS and content:** draft/published/archived isolation, session-gated previews, restore/publish behavior, permanent-delete policy, owner-only SEO, Markdown sanitization, and stored/reflected XSS surfaces.
- **Database and APIs:** parameterized query use, IDOR boundaries, response/error handling, method restrictions, no-store behavior, throttles, and security headers.
- **Code/deployment hygiene:** dependencies/advisories, environment-variable use, secret markers, debug/health routes, dead-code/lint signals, and credential-free build behavior.
- **Accessibility/quality:** source-level checks plus rendered Playwright/axe checks for labels, field errors, landmarks, dialogs, status text, live regions, image alternatives, keyboard focus behavior, reduced motion, responsive layout, and default-theme contrast. Browser coverage and its remaining manual-testing limits are documented in §8.

All adversarial tests and live probes were local. There were no destructive tests against production and no production database writes.

**Local HTTP probe results:** owner settings/SEO reads returned **200**; editor settings/SEO reads returned **403**, while an editor service-list read remained **200**. A public-library upload carrying CV purpose returned **400**. Traversal-shaped and unknown public-media paths returned **404**; unsupported HTTP methods returned **405**. SQL-injection-shaped service search values returned **200** with no matching data or SQL error. Local admin responses showed the configured per-request nonce-based CSP (including `frame-ancestors 'none'`) and security headers: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()`, `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`, and `X-DNS-Prefetch-Control: off`. The session cookie is `HttpOnly`, `SameSite=Lax`, and `Secure` in production; the CSRF cookie is intentionally JS-readable and validated against both the request header and session-stored secret. D18’s private-media read/mutation denials are verified by isolated route integration tests, not presented as production or browser observations.

A source sink scan found one `dangerouslySetInnerHTML` use: FAQ JSON-LD built with `JSON.stringify`, with angle brackets escaped before insertion. No raw `innerHTML`/`outerHTML`, `eval`, `new Function`, or browser `localStorage`/`sessionStorage` usage was found in the reviewed application source. This is a static source finding, not a dynamic XSS certification.

## 3. Defects corrected

1. **D12 — public CV/media-purpose bypass:** `src/lib/cms/media.ts` now refuses both `purpose === 'cv'` and any detected document before `buildStorageKey()` can produce a public key. The public proxy’s document allowlist and the media-library UI exclusion remain in place as defense in depth.
2. **D13 — redirect sanitization:** `src/app/(admin)/admin/login/login-form.tsx` rejects C0/DEL control characters and backslashes before accepting a local relative destination. `src/middleware.ts` only attaches a single-slash same-site pathname to the login URL.
3. **D14 — mobile navigation modality:** `src/components/site/mobile-nav.tsx` and `src/components/admin/admin-shell.tsx` now focus into their drawers, trap Tab/Shift+Tab, close on Escape, and restore focus. The admin drawer also uses a named modal dialog, locks background scrolling, and makes the underlying header/sidebar/main inert. Public-menu and admin-drawer behavior was verified in the isolated Chromium run (§8).
4. **D15 — owner-only read API checks:** `guardRead()` now supports role sets; SEO resource reads use an owner-only set and site-settings GET explicitly requires `owner`. Owner writes remain guarded by the existing role/CSRF sequence.
5. **D16 — low-contrast neutral text:** visible `text-slate-400` usages in `src` were moved to `text-slate-600`. A regression assertion prevents the low-contrast utility from returning in application source.
6. **D17 — consistent CMS write throttle:** the shared durable helper in `src/lib/cms/api.ts` is now used by collection/item writes, publish/restore/reorder, settings, upload, media metadata, and media archive/restore routes. Assessment mutations retain their existing separate per-admin throttle.
7. **D18 — public/private media boundary:** the generic media-by-ID endpoint selects only the fields needed by the media UI, requires `visibility='public'` and a `public/` key, and never serializes `storageKey`. The media metadata/archive/restore helpers enforce the same public-only rule.
8. **Prior-report correction:** `docs/PHASE-6-REPORT.md` incorrectly said Phase 4 defects D1–D11 remained open. Phase 4 §4 records them as corrected; the Phase 6 line was corrected, and Phase 7 regression testing did not reproduce them.
9. **D19 — dashboard reflow:** `src/app/(admin)/admin/(dashboard)/page.tsx` now sets an explicit single-column base grid and `min-w-0` on the cards, preventing a content-dependent 25px overflow at 375px.
10. **A11Y-2 — admin control names:** `src/components/admin/admin-shell.tsx` derives the account disclosure's name from its initials/name and screen-reader text; `src/components/admin/assessments/assessment-list.tsx` includes “Descending” or “Ascending” in the sort toggle's accessible name. Final axe scans found no violations on the covered views.
11. **Public responsive/accessibility polish:** the site logo now has an accessible name, mobile reveal offsets are reduced to 16px, and service/destination listing cards accept the page's correct heading level to preserve heading order.
12. **A11Y-1 — configurable brand palette:** `src/lib/brand-colors.ts` now centralizes WCAG ratios and per-token surface requirements; CMS schema/API validation and the settings-form preview use the same rules. Existing invalid stored values are replaced per token with accessible defaults at read time. `brandTextColor` and `brandActiveColor` now feed visible public styles, and active mobile navigation uses the active token rather than the primary red.
13. **Follow-up axe cleanup:** the mobile logo link's accessible name begins with its visible “SA” monogram; MediaPicker file inputs reference their visible labels with `aria-labelledby`; and alert Dismiss buttons retain readable contrast without opacity reduction. These changes were included in the final 14-scan axe run.
14. **D20 — testimonial grid reflow:** `src/app/(site)/page.tsx` and `src/app/(site)/testimonials/page.tsx` now declare `grid-cols-1` at the base breakpoint while preserving the existing two- and three-column breakpoints. This removes the intrinsic-width overflow without redesigning cards or changing the responsive layout above the base breakpoint.
15. **A11Y-3 — assessment hint/error references:** `src/components/ui/field.tsx` adds the hint ID to `aria-describedby` only when `hint && !error`, matching the content actually rendered. `tests/ui-accessibility.test.ts` adds source regression checks; the final rendered check confirmed label, visible hint, and visible error associations.
16. **Forced password-change verification (no app-code change):** a newly seeded owner in the isolated scratch database logged in with `mustChangePassword=true`; direct `/admin` access returned to `/admin/change-password`; successful password change returned 200 and immediately navigated to `/admin`. The same HttpOnly session cookie remained active, its hash matched the one active database session, its CSRF cookie matched the session row, and the admin's mandatory-change flag cleared with a password-change timestamp. This verified the existing behavior; `change-password-form.tsx` was not changed.

No database columns, tables, indexes, migrations, or production settings were changed.

### Remediation, verification, and remaining compatibility risk

- Added the narrow override `"@esbuild-kit/core-utils": { "esbuild": "0.25.12" }` to `package.json` and refreshed the lockfile. Direct versions remain `drizzle-kit@0.31.11` and `next@15.5.29`; no broad update, downgrade, or `npm audit fix` was used. Existing `postcss@8.5.32` and `@typescript-eslint/typescript-estree.minimatch@11.0.4` overrides were retained.
- Current tree from `npm ls --all esbuild postcss @esbuild-kit/core-utils @esbuild-kit/esm-loader drizzle-kit`: `drizzle-kit@0.31.11` → `@esbuild-kit/esm-loader@2.6.5` → `@esbuild-kit/core-utils@3.3.2` → overridden `esbuild@0.25.12`; Drizzle Kit also resolves `esbuild@0.25.12`; `tsx@4.23.15` uses its separate `esbuild@0.28.2`; Next.js and Tailwind resolve `postcss@8.5.32`. No `esbuild <=0.24.2` remains and npm reports no invalid dependency.
- **Compatibility caveat:** `@esbuild-kit/core-utils@3.3.2` declares `esbuild ~0.18.20`; the security override intentionally crosses that declared range. The used Drizzle config-loader operations (`db:check`, `db:generate`) passed with `0.25.12`, and typecheck, lint, all 409 tests, schema verification, and the credential-free production build passed afterward. This is exercised compatibility for the paths used here, not an upstream guarantee for every loader feature or future Drizzle Kit release. No Drizzle loader failure has been observed. Keep the pin and regression checks until Drizzle Kit replaces the deprecated loader or an approved migration is completed.
- **Compatibility risk and alternatives (registry checked 4 November 2026):** latest `drizzle-kit@0.31.11` still depends on deprecated `@esbuild-kit/esm-loader@^2.5.5`, whose `@esbuild-kit/core-utils@3.3.2` metadata declares `esbuild ~0.18.20`. The override to `0.25.12` could expose untested loader/runtime assumptions or break on a future Drizzle Kit/config-loader path even though current checks pass. Reasonable choices are: retain the narrow security override with audit, `db:check`, `db:generate`, and regression gates; wait for an upstream Drizzle Kit/loader update that removes the deprecated loader, then reassess and remove the override only when safe; or maintain a small tested patch/fork if upstream does not move in time.
